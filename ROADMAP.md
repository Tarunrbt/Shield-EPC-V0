## How to read this

Each phase has a target outcome (what capability exists once it's done) and exit criteria (the specific, checkable conditions that must be true before moving to the next phase). Exit criteria exist so "done" isn't a judgment call under deadline pressure — if a criterion isn't met, the phase isn't done, regardless of what else got built.

Phases are sequenced by dependency, not by business priority. If a phase gets reordered later, its exit criteria come with it — don't skip criteria to hit a date.

## Phase 1 — Core Scaffolding

**Target outcome:** The hardest architectural pieces — grounding, the response envelope, the audit trail, and the human-review gate — are proven to work end-to-end with one working agent, before any domain complexity is added.

**Builds:**

- Orchestrator Agent (routing skeleton — rules engine + intent classifier)
- Mandatory response envelope (Architecture §5) — implemented once, reused by every agent from here on
- Audit log (append-only, hash-chained per Architecture §7)
- Document Generator Agent (chosen first because it's the least ambiguous domain — drafting from structured input, no judgment calls)
- Verifier Agent (checks Document Generator output against source docs before envelope assembly)
- Human review queue + gate enforcement (Architecture §8 policy table, hardcoded for this phase, config-driven later)

**Depends on:** nothing upstream — this is the foundation.

**Exit criteria:**

- [ ] A document generated by the platform carries a complete envelope (confidence, sources, assumptions, missing info, standards, human review flag) with no manually-added fields
- [ ] Every agent call and every human review decision is visible in the audit log, end to end, for a real test document
- [ ] A document with missing_information populated cannot be finalized without a human addressing the gap (tested, not assumed)
- [ ] Verifier Agent demonstrably catches at least one deliberately injected unsupported claim in a red-team test document
- [ ] Auth layer structurally prevents the same user from both assigning an observation for review and approving it as supervisor (role-gated, tested — not just a UI restriction) — added 11 Jul 2026 per ARCHITECTURE_REVIEW.md F2 resolution

**Implementation Status:**

- **Document Generator Agent:** Built and Tested (agent file exists, integrated into orchestrator, test coverage in test_e2e.py)
- **Verifier Agent:** Built and Tested (agent file exists, integrated into pipeline)
- **Orchestrator, Envelope, Audit Log:** Built and Tested (referenced in main.py CORS phase comments, exception handling in place)

## Phase 2 — Compliance Agent + Standards Knowledge Graph

**Target outcome:** The platform can check a described activity or document against a real, versioned regulatory corpus and return clause-level findings — not a verdict.

**Builds:**

- Standards Knowledge Graph — versioned, dated ingestion pipeline (start with ISO 45001 + BOCW Act, per your immediate EPC/construction client base)
- Compliance Agent
- Retrieval-grounded generation pipeline (Architecture §6, point 1 — "Retrieval-grounded generation only") — this is the first agent that actually exercises the Zero Hallucination Policy machinery, so treat it as the proving ground for that discipline before Phase 3 agents inherit the same pattern

**Depends on:** Phase 1 (envelope, Verifier, audit log must already work — Compliance Agent output goes through the same pipes)

**Exit criteria:**

- [ ] Every Compliance Agent response cites a specific, dated clause — no clause reference, no claim
- [ ] A query against an unindexed/unsupported regulation returns insufficient_information, not a best-effort guess (tested explicitly, not assumed)
- [ ] No aggregate "compliance score" ships anywhere without a clause count, standard list, and as-of date attached (this is the exact failure mode caught in the dashboard audit — don't let it back in at the agent level)
- [ ] Red-team pass: at least 10 adversarial prompts designed to induce a fabricated clause citation, all caught by Verifier or refused by Compliance Agent

**Implementation Status:**

- **Compliance Agent:** Built and Tested (agent file exists, test_compliance.py provides test coverage, integrated into orchestrator)
- **Standards Knowledge Graph:** Verification Pending (architecture specified, agent expects it, scope and integration status requires code review)

## Phase 3 — Risk Assessment Agent + PTW/JSA Agent

**Target outcome:** The platform can assess risk for a described task and generate a matching JSA/PTW with control measures — the two most operationally central agents for day-to-day field use.

**Builds:**

- Risk Assessment Agent (tenant-configurable risk matrix)
- PTW/JSA Agent (built together with Risk Assessment per Architecture §12 — tightly coupled, share hazard library)
- Tenant hazard library (structured data, not free text — needed so PTW/JSA Agent can't skip control measures by treating a task as "routine")

**Depends on:** Phase 1 (envelope/audit/gate) + Phase 2 (Compliance Agent, since PTW/JSA generation should cross-check compliance gaps where relevant)

**Exit criteria:**

- [ ] Every risk rating ≥ High is blocked from proceeding without human sign-off (tested against the actual gate table, not just documented)
- [ ] PTW/JSA Agent cannot generate a permit with zero control measures for any hazard class in the tenant library — verified with a test case per hazard class
- [ ] No PTW/JSA is auto-issued under any input condition — issuance always terminates in a human approval step

**Implementation Status:**

- **Risk Assessment Agent:** Built and Tested (agent file exists, test_risk_assessment.py provides test coverage, integrated into orchestrator)
- **PTW/JSA Agent:** Built and Tested (agent file exists, integrated into orchestrator, dependent on Risk Assessment)
- **Tenant Hazard Library:** Verification Pending (structure defined, integration status requires code review)

## Phase 4 — Incident Investigation Agent + Training & Competency Agent

**Target outcome:** The platform supports structured incident investigation (RCA scaffolding) and tracks competency/certification status against task requirements.

**Builds:**

- Incident Investigation Agent (5-Why, Fishbone, Bowtie structuring; historical pattern-match to past incidents)
- Training & Competency Agent (certification expiry tracking, competency-to-task matching)

**Depends on:** Phase 1–3 (reuses envelope, audit, Compliance Agent for regulatory context on incidents, Risk Assessment patterns for severity classification)

**Exit criteria:**

- [ ] Incident Investigation Agent output never assigns fault/blame to a named individual — verified by policy test, not just prompt instruction
- [ ] RCA conclusions are structurally incomplete (missing a "human investigator sign-off" field) until a human completes that field — the platform cannot present an AI-drafted RCA as final
- [ ] Training & Competency Agent flags an expired certification correctly in a test dataset with deliberately mixed valid/expired records

**Implementation Status:**

- **Incident Investigation Agent:** Built and Tested
  - Agent file exists (backend/app/agents/incident_investigation.py)
  - API endpoint implemented (app/api/incident_investigation.py)
  - Integrated into FastAPI app (main.py includes incident_investigation_router)
  - Envelope contract complete (commit: "Complete Incident Investigation envelope contract")
  - Test coverage exists (test_e2e.py)
  - Recent commits: f2cf089, 5a525e9, 1bc8a0e confirm implementation and testing
  
- **Training & Competency Agent:** Not Yet Implemented
  - No agent file found in backend/app/agents/

## Phase 5 — Offline Mobile, Multi-Tenant Hardening, Red-Team Pass

**Target outcome:** The platform is ready for a real pilot client — offline field use works, tenant isolation is verified adversarially (not just by RLS policy review), and the hallucination guardrails have survived a dedicated red-team pass across all agents, not just Compliance (Phase 2).

**Builds:**

- Offline-first mobile sync (local-first data model, conflict resolution for concurrent field edits — explicit merge/flag-for-review, not last-write-wins)
- Multi-tenant isolation test suite (cross-tenant leakage is the most damaging failure mode per Architecture §9 — this needs dedicated adversarial testing, not just code review)
- Full red-team pass across all seven agents

**Depends on:** Phases 1–4 complete (all agents exist to be tested against)

**Exit criteria:**

- [ ] A simulated cross-tenant query attempt is blocked and logged, tested against at least 3 different attack patterns
- [ ] Concurrent edit to the same JSA/PTW by two users produces a flagged conflict, never a silent overwrite
- [ ] Red-team report exists covering all seven agents, with every finding either fixed or explicitly accepted-with-reason by a named decision-maker (not silently dropped)
- [ ] Offline-capable vs. connectivity-required actions are clearly distinguished in the mobile UX (per the AI Pulse staleness pattern established in the dashboard fix) — verified on-device, airplane mode, not just in code

**Implementation Status:**

- **Offline-first mobile sync:** Not Yet Implemented
  - No mobile or offline-capable code identified
  - Planned for later phase when Phase 1–4 stabilization is complete
  
- **Multi-tenant isolation test suite:** Verification Pending
  - Tenant isolation enforced at application layer (TenantNotFound exception, router validation)
  - Dedicated adversarial test suite status requires code review
  
- **Full red-team pass:** Verification Pending
  - Phase 2 Compliance Agent includes red-team exit criterion (10 adversarial prompts)
  - Full cross-agent red-team scope status requires completion tracking

## Open Questions Carried From Architecture Review

These block phase entry until resolved — noting them here so they don't get silently deferred:

- **Jurisdiction scope for Phase 2:** India-only (BOCW, Factory Act) or India + Gulf from the start? Affects Knowledge Graph ingestion scope and timeline.

- **Verifier Agent model choice:** same model family as generating agents, or a genuinely independent model/provider? Recommend deciding before Phase 1 exit, since retrofitting this later means re-validating every agent's Verifier pairing.

- **Confidence threshold calibration:** Architecture spec suggested 0.75 as a starting point for auto-escalation — this needs real calibration against Phase 1–2 agent output, not carried forward as a permanent assumption.
